Webot AI Telegram Support Bot — Build Workflow

Step 1: Understand the Requirements

  • Goal: AI customer support bot on Telegram for Webot (formerly Pionex.US)
  • Users chat with the bot → AI answers from knowledge base
  • If AI can't answer → escalate to human agent
  • Agent receives ticket via a separate agent bot and can reply back to user

Step 2: Choose the Tech Stack

ComponentTechnologyReason
ServerNode.js + ExpressLightweight, handles webhooks and polling
MessagingTelegram Bot APITwo bots: customer bot + agent bot
AI ModelAWS Bedrock (Claude Haiku)Fast, cost-effective, multilingual
StorageJSON filesNo database needed for demo stage

Step 3: Build the Telegram Layer

  • Set up Express server with /webhooks/telegram endpoint
  • Support both polling mode (local dev) and webhook mode (production)
  • Parse incoming messages and route to the correct handler
  • Two bots polling independently: customer bot + agent bot

Step 4: Build the Knowledge Base

Files

  • data/knowledge-base.json — business summary, FAQ list, handoff contact
  • data/docs/ — additional product documents (.md, .txt, .csv)

How it works

  • FAQ keyword matching runs before calling AI (faster and cheaper)
  • Relevant documents are scored and passed as context to the AI
  • Unanswered questions are logged to data/gap-log.jsonl for review

Step 5: Build the AI Response Engine

  • Connect to AWS Bedrock (Claude Haiku model)
  • Build system prompt from: knowledge base + FAQ context + matched documents
  • Detect user's language from message.from.language_code → respond in Chinese or English
  • Multi-turn conversation history per user (in-memory, expires after inactivity)
  • AI returns structured JSON: {"intent": "answer"|"handoff", "reply": "..."}

Step 6: Build the Handoff System

Triggers

  • Keyword trigger — "人工", "human", "urgent" etc. → instant handoff, no AI call
  • AI-triggered — AI returns intent: "handoff" when it can't answer

Session management

  • In-memory handoffSessions map tracks active user↔agent connections
  • Each session gets a 4-character ref (e.g. #EAVO)
  • Agent bot sends ticket notification with conversation history + available commands

Step 7: Build the Agent Relay

Agent bot commands

CommandAction
REPLY <message>Reply to the only active session
REPLY #REF <message>Reply to a specific session by ref
RESOLVEClose the active session
SESSIONSList all active sessions

Two-way relay

  • User messages during handoff → forwarded to agent via agent bot
  • Agent REPLY → forwarded to user via customer bot
  • Only chat IDs in AGENT_CHAT_IDS can use agent bot commands (security)

Step 8: Bug Fixes & Hardening

  • Fixed notification sent via wrong bot (telegramClient → agentBotClient)
  • Added isAgentChat() check on agent bot polling — blocks unauthorized accounts
  • Language detection from message.from.language_code for Chinese/English responses
  • Gap logging — unanswered questions saved to data/gap-log.jsonl

Step 10: Deployment

Local (development)

  • Set TELEGRAM_MODE=polling — no public URL needed
  • Run: npm start or node src/index.js
  • Only one instance at a time — two instances cause 409 polling conflict

Production (recommended options)

  • Railway — easiest, connect GitHub repo, set env vars in dashboard
  • AWS Lightsail — $5/month VPS, use pm2 to manage process
  • Render — free tier available, good for low traffic

Production process manager

npm install -g pm2
pm2 start src/index.js --name webot
pm2 startup && pm2 save
